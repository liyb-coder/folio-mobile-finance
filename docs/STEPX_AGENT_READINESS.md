# Folio × 智能手机终端 Agent 可行性

更新：2026-08-11  
结论：**可以做，但最合理的形态是“终端系统 Agent 调度 + Folio 财务整理 Skill/工具 + Folio 核对界面”，而不是让 Folio 自己变成一个拥有所有系统权限的超级 Agent。**

## 1. 从第一性原理看用户价值

普通用户不需要另一个会聊天的财务助手，他们需要的是：

1. 不用打开表格，随时说出刚刚发生的收入、支出和提醒；
2. 系统能把一段混合表达拆成几个清楚项目，不丢失任何一项；
3. 不必每天开着 App，也能在该交保费、交房租、处理到期资金时获得提醒；
4. 长期记录逐渐变成一张能解释的财务地图，帮助用户看见现金流、到期节点和可规划资金。

这与智能终端的价值匹配：终端负责感知和调度，Folio 负责财务语义、证据、核对、账本与提醒规则。

## 2. 适合活动展示的主链路

**一句混合语音 → 终端语音转文字 → Folio 拆分待核对项 → 用户逐项确认 → 更新地图和提醒。**

演示口令：

> 建行新增租金收入 8,000，8 月 20 日提醒我交保费 10,000，然后帮我看下这个月还有多少活钱可以规划。

终端 Agent 的任务计划：

1. 调用 `folio.create_review_proposal`，产生收入和提醒两个待核对项；
2. 打开 Folio 核对卡片，保留每个项目的语音原文证据；
3. 终端 Agent 只能打开 Folio 前台核对页；用户在 Folio 内重新验证并逐项确认后，Folio 才在本地原子提交账本与提醒；
4. 调用 `folio.get_planning_snapshot`，使用已确认账本计算活期可用；
5. 返回“可规划金额 + 已预留提醒 + 计算依据”，不自动买卖产品。

这条链路同时证明了感知、规划、工具调用、结果可验证和高风险动作的人机边界。

## 3. Agent 工具面

| 工具 | 用途 | 风险级别 | 终端是否可直接执行 |
|---|---|---:|---|
| `folio.create_review_proposal` | 将文字/语音转写/图片提取文本拆成待核对项 | 中 | 可以，但只能产生 `pending_review` |
| `folio.list_due_reminders` | 查询到期、保费、租金和空闲资金提醒 | 低 | 解锁后可读 |
| `folio.get_planning_snapshot` | 返回净资产、活期可用、近期必要支出和证据覆盖 | 中 | 只读，金额按授权最小化 |
| `folio.open_review` | 打开指定提案的 Folio 核对界面 | 低 | 可以 |
| `folio.simulate_idle_cash_plan` | 基于当前数据做规划沙盘 | 中 | 只能模拟，与真实交易分离 |

`folio.confirm_selected_items` 只保留在 Folio 内部运行时，**不进入 STEPX 公开工具注册表**。终端层不公开付款、转账、买入、卖出、交易或代用户确认的任何能力。

## 4. Agent 自主程度

- L0：回答问题。
- L1：将输入整理成有证据的待核对项。**Folio 当前最应该做好。**
- L2：跨时间检查到期事项、现金覆盖和可规划资金，主动提案。**活动演示可达到。**
- L3：在用户明确确认后更新账本、创建提醒。**只允许 Folio 前台应用在重新验证后执行，不属于终端 Agent 权限。**
- L4：跨应用调度并自动买基金、付款、转账。**不纳入 MVP，也不应在活动中伪装已实现。**

## 5. 载体差异

### STEPX / Step AOS

如果活动主办方提供 Skill/工具注册、权限、深链和真机调试规范，Folio 可以作为财务领域 Skill 接入 Amoo。目前公开页面可以确认阶跃模型平台对 MCP/Skills 等 Agent 协议做了兼容优化，但没有找到足以实现 Step AOS 系统集成的公开 SDK 规范，因此需要现场或主办方资料才能完成最后适配。

### iOS

iOS 可以通过 App Intents 把“记一笔”、“查看近期提醒”和“打开待核对项”暴露给 Siri、快捷指令和系统入口。它能成为“可被系统 Agent 调用的财务应用”，但不是任意控制其他 App 的系统级 Agent。后台任务也由系统调度，不是永不停止的常驻进程。

### 微信小程序

小程序适合低门槛采集、核对和查看，不适合承担系统级跨 App 调度。它可以成为 STEPX 演示的备用界面，但 Agent 工具层应该位于 Folio BFF，而不是小程序包内。

## 6. 活动前必须向主办方确认

1. Step AOS/Amoo 的 Skill 注册格式、调用协议和示例代码；
2. 真机测试账号、设备、签名和调试权限；
3. 是否支持 HTTPS BFF、MCP、深链、回调以及交互卡片；
4. 财务数据、金额和本地生物识别的权限/审核规范；
5. 是否允许应用在工具返回中要求“必须前台人工确认”；
6. 活动现场网络、域名白名单和可否使用开发/预发服务。

## 7. 只读信息源与迭代路径

- **银行 App**：不尝试绕过禁止截图、访问辅助或安全键盘限制；不注入、不爬取、不代操作。
- **银行短信**：只在 Step AOS 明确提供并通过审核的只读短信权限下读取；按发送方白名单筛选，原文作为证据，仅生成 `pending_review`。
- **QQ 邮箱**：使用只读 OAuth/应用授权，限定账单发送方和标签；不发信、不删信、不改已读状态。
- **截图/PDF**：用户主动选择后在设备端抽取文字，保留页码或坐标证据，用完即释放原文件；不绕过上游应用的截图禁止。
- **语音/文字**：当上游数据无法安全读取时，回退到用户主动口述或输入，缺少账户、金额或日期则失败关闭。

上述所有路径的最高结果都只是待核对提案，不能把信息读取权限扩展为资金操作权限。

## 8. 建议的活动交付物

- 一个真实可说的混合语音案例；
- 一个 Folio Agent Skill 适配器，仅开放 4–5 个工具；
- 一个小程序/手机核对卡片；
- 一个本地虚构账本与不可变操作记录；
- 一个失败场景：模型缺少证据或试图跳过确认时，Folio 明确拒绝。

展示定位可以是：

> **Folio 是智能终端里的财务整理 Skill：用户只说一次，AI 把变化整理成可验证的行动，账和钱始终由用户确认。**
