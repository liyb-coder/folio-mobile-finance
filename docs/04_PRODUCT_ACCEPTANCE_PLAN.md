# Folio 真实产品开发与验收计划

更新：2026-07-30

## 1. 完成定义

Folio 只有同时满足以下条件，才算“真实产品”而不是前端 Demo：

1. 正式模式从空的 SQLCipher 保险库启动，不自动注入演示数据。
2. 账户、持仓、流水、事项、规划、AI 收件箱和审计均由 Rust 原生命令读写真实数据库。
3. 金额在 Rust 中转换为整数最小货币单位；禁止用 JavaScript 浮点数作为事实源。
4. 语音、文件、邮箱和模型只能产生待核对候选；明确确认前不得改变账本。
5. 应用重启、锁定与重新解锁后，已确认数据保持一致，未确认草稿仍可追溯。
6. API Key 不进入 React、Vite、SQLCipher、日志、测试快照或 Git。
7. 从干净保险库导入指定 Markdown 后，能够覆盖主要产品模块并完成对账。
8. 自动化测试、真实 API 最小测试、桌面与移动 UI 走查全部达到退出标准。

## 2. 技术事实源

| 层 | 正式实现 | 验收要求 |
|---|---|---|
| UI | React 19，共享桌面/移动体验 | 不允许用前端 Mock 冒充本机数据 |
| 原生应用 | Tauri 2 | 所有敏感命令显式注册，无 Shell 权限 |
| 后端 | Rust | 校验、事务、导入、AI 网关、通知和备份均在原生层 |
| 数据库 | SQLite + SQLCipher | 整库加密、外键、不可变账本/审计、幂等写入 |
| 密钥 | 应用密码封装 DEK；Keychain 保存设备密钥和用户 API Key | 密钥不返回前端 |
| AI | Provider Adapter；首个外部实现为 OpenAI Responses API | `store:false`、Structured Outputs、逐次外发授权 |
| 文件 | PDFKit/Vision/本地文本解析 | 原件默认不持久化，只保存必要证据 |
| 邮件 | QQ 邮箱只读 IMAP，专用授权码 | 只生成待核对流水，不修改或删除邮件 |

## 3. API Key 决策

### 开发与自动化测试

Rust 原生层只检查白名单变量：

- `FOLIO_OPENAI_API_KEY`
- `OPENAI_API_KEY`
- `FOLIO_OPENAI_MODEL`
- `FOLIO_OPENAI_BASE_URL`

应用只向 UI 返回“已配置/来源/模型名称”，不返回密钥。

### 正式桌面应用

用户在“设置 → AI 模型”中填写 API Key，经明确确认后直接存入 macOS Keychain。React 提交后立即清空输入框；SQLCipher 只保存非敏感配置和审计摘要。

环境变量只用于开发，因为从 Finder 启动的 macOS App 不可靠继承终端 Shell 环境。

### 明确不采用

- 不在 `VITE_*` 环境变量中保存 Key；
- 不扫描全部环境变量；
- 不把 Key 写入 `.env`、数据库或日志；
- 不假设安装后的 Folio 可以调用当前 Codex 任务内部模型。

## 4. AI 数据路径

```text
文字 / 设备内语音转写 / OCR / Markdown
→ 用户选择本地规则或明确同意外部模型
→ Rust Provider Gateway
→ OpenAI Responses API（store:false）
→ JSON Schema 结构化事实
→ Rust 检查枚举、数量、置信度与逐字证据
→ 多条 CapturedItem / Proposal
→ 对应领域 needs_review 草稿
→ 用户逐条修订或明确确认
→ SQLCipher 单事务正式写入与审计
```

模型输出保留 `amountText` 原文。Rust 领域层重新解析金额，不能接受模型计算得到的隐含金额；证据文字不在原文中则整条安全失败。

## 5. 分阶段开发顺序

### 阶段 A：真实后端基线

- [x] SQLCipher 保险库、不可变账本、账户/持仓/流水/事项/规划。
- [x] 加密备份、恢复、明文可移植导出和审计。
- [x] 持久 AI 提案列表。
- [ ] OpenAI Provider 设置、连接测试和结构化事实抽取。
- [ ] 外部 Provider 输出转为多条领域草稿。

### 阶段 B：冷启动全量注入

- [ ] 从空保险库选择 Markdown。
- [ ] 一份文档拆分账户、持仓、流水、事项、规划、保险和法律事项。
- [ ] 依赖排序：账户 → 持仓 → 流水 → 事项 → 规划。
- [ ] 显示重复、冲突、缺字段和不支持项目。
- [ ] 支持逐条与分组确认，但每条正式变化仍可独立审计。

### 阶段 C：真实输入连接

- [ ] QQ 邮箱只读 IMAP、Keychain 授权码、白名单和增量游标。
- [ ] 邮件消费、退款、撤销、预授权和账单汇总分类。
- [ ] 多模态文件、语音和邮件统一进入 AI 收件箱。

### 阶段 D：移动与发布

- [ ] 完整 Xcode/CocoaPods 和 Android 工具链。
- [ ] iOS/Android 真机权限、后台锁定、截图/文件和通知验收。
- [ ] Developer ID 签名、公证、升级保留数据和异常恢复。

## 6. 质量门

### 自动化

- JavaScript 领域/UI 合约测试全部通过；
- Rust 单元与数据库事务测试全部通过；
- SQLCipher 文件头、错误密钥、篡改与不可变触发器测试通过；
- `npm run build` 与 `npm run test:sites` 通过；
- 仓库隐私扫描确认没有真实数据和密钥。

### 真实 API

- 环境变量只报告 presence，不输出值；
- 连接测试返回预期标记；
- 至少一条真实 Structured Output 抽取通过；
- 证据不在原文、金额模糊、模型拒绝、401、403、429、超时均安全失败；
- 任何 API 失败不改变账本。

### 冷启动端到端

- 从零账户、零流水、零事项开始；
- 注入 `docs/demo/Folio_冷启动全量演示数据.md`；
- 未确认阶段所有余额仍为零；
- 确认后 CNY 账户余额、持仓内部分解和流水守恒精确；
- USD 在无汇率时不并入 CNY 汇总；
- 重复注入不重复加账；
- 退出重开后数据一致；
- 备份恢复后的记录数、余额与来源指纹一致。

### UI

- 390×844 与 1280×720 无横向溢出；
- 主操作、弹窗、核对、错误、空状态、处理中和完成状态可达；
- 桌面猫猫只提示“待核对”，不能暗示模型已替用户完成财务变更；
- 移动端不常驻桌宠，底部中央录入入口始终可达；
- 浏览器/原生运行时无未处理错误。

## 7. 缺陷标准

- P0：数据丢失、重复加账、密钥泄漏、绕过确认、账本不守恒。
- P1：主流程不可完成、错误数据进入正式账本、恢复结果不一致。
- P2：重要状态不清晰、移动控件不可达、明显布局或交互问题。
- P3：不阻塞使用的视觉与文案优化。

发布候选要求 P0/P1/P2 为零；P3 必须记录并说明是否延期。
